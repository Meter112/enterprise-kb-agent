# 检索评估报告 v1（D11-14）

> 评估对象：检索链路（hybrid RRF + rerank + 拒答 + 权限过滤），不含 Agent 生成层。
> 评估集：`data/qa_sets/qa_set_v1.json`（32 条 × 4 场景），gold chunk 为 Qdrant point id 精确匹配。
> 环境：CPU-only（torch 8 线程），BGE-M3 dense + 手写 jieba BM25 sparse + bge-reranker-base，Qdrant 单机。
> 时间：2026-10-10。报告 JSON：`data/reports/eval_*.json`。

## 1. 评估集构成

| 场景 | 条数 | 说明 |
|---|---|---|
| single_hop | 16 | 单文档事实型，覆盖 4 个权限层级 |
| multi_doc | 5 | 跨文档对比/聚合 |
| no_answer | 5 | 语料外问题（应拒答） |
| permission | 6 | 目标文档对请求角色不可见（应拒答，gold 仅报告用） |

gold 总数 85（索引重建前 73——同名 MD/PDF doc_id 碰撞 bug 曾覆盖删除 12 个 chunk，已修复）。

## 2. 消融对比（v1）

| 模式 | Hit@5 | MRR | 拒答准确率 | 漏拒率 | 平均延迟/条 |
|---|---|---|---|---|---|
| hybrid（RRF+rerank） | 0.741 | 0.560 | 0.781→**0.938**¹ | 0.636→0.182¹ | 17.84s |
| hybrid_no_rerank | 0.704 | 0.605 | 0.656 | 1.000 | 0.66s |
| dense | **0.778** | **0.657** | 0.656 | 1.000 | 0.63s |
| sparse | 0.630 | 0.494 | 0.656 | 1.000 | 0.65s |

¹ 拒答阈值为 0.3（初始值）时；标定到 0.7 后的离线重算值。

**发现 1：dense 单路在小语料（370 chunks）上 Hit@5/MRR 全面高于 hybrid。** RRF 融合把 sparse 的弱相关结果带入 top-5，挤掉了 dense 的 gold 位置。诚实的结论是：当前语料规模下混合检索没有带来指标增益——但这不代表 hybrid 没用：稀疏路是词面匹配保障（术语/编号/代码），在未覆盖问题上是安全网，且企业语料增长后两路互补性才会显现。v2 改进方向：RRF k 值调参、dense 分数加权、或 dense 优先 + sparse 兜底。

**发现 2：rerank 提升 Hit@5（0.704→0.741）但降低 MRR（0.605→0.560）。** reranker 找回了 1-2 条 RRF 漏排的 gold，但把部分 gold 从第 1 位移走（top1 变成同文档的相关但非 gold chunk，见 §5 口径讨论）。净效果为正但排序精度有扰动。

**发现 3：rerank 是绝对延迟瓶颈**（16.8s / 17.8s 的 94%），no_rerank 模式 0.66s/条。优化方向：rerank 候选 50→20（召回 0.05s 说明前置阶段极快）、FP16、或小语料下按需启用。

## 3. 拒答阈值标定

方法：hybrid 评估快照 top-5 分数，**离线重算**各阈值下的拒答双面指标（`scripts/scan_threshold.py`），不重复跑检索（每条 ~18s × 32 条 × 12 阈值 ≈ 2 小时 → 1 秒）。

| 阈值 | 准确率 | 漏拒率 | 误拒率 |
|---|---|---|---|
| 0.30（初始） | 0.781 | 0.636 | 0.000 |
| 0.50 | 0.844 | 0.455 | 0.000 |
| **0.70（选定）** | **0.938** | **0.182** | **0.000** |
| 0.85 | 0.938 | 0.182 | 0.000 |
| 0.90 | 0.938 | 0.000 | 0.095 |

**选 0.70**：0.70-0.85 是帕累托最优区间（漏拒率 0.182、误拒率 0），取区间下界更保守（对漏拒——越界信息风险——更严格）。0.90 才开始误伤正例。

**阈值救不了的 2 条漏拒**（top1 分数）：qa-029「财务付款流程」0.881、qa-030「内部订单API创建订单」0.870——可见语料中的弱相关文档分数与正例区间重叠，检索层无法区分。这两条留给 Week 3 Agent 层：生成前校验 + 引用支撑检查，答不上来就明说。

## 4. 权限与拒答正确性

- **权限过滤 0 泄漏**：6 条 permission 题 top-5 全是可见层级文档，目标文档从未出现（qa-027 contractor 查年假 → 只有 public/contractor 文档）。
- **0 误拒**：21 条应答题在阈值 0.7 下全部通过（应答侧 top1 最低 0.85+）。
- 漏拒 7→2（标定后）：剩余 2 条见上。

## 5. judge 抽查（flash，n=8）

一致性 0.625。逐条归因后发现**不是 judge 质量问题，是评估口径错配**：

- judge 判 top1 文本能否回答问题，hit 看 top-5 是否含 gold → qa-001（top1=年假申请流程，gold=年假天数在 top-5 更后）、qa-009、qa-013 的"不一致"实为口径差。
- qa-017/021（multi_doc 对比）judge 判"top1 只覆盖对比的一面，不足以回答"——judge 是对的，且指向真问题：**跨文档对比需要 Agent 层多次检索聚合**，单次 top-5 召回不是为此设计的（Week 3 query_kb 工具的动机）。

v2 修正：judge 改为判"top-5 拼接文本是否足以回答问题"，与 hit 口径对齐。

## 6. 结论

1. 检索链路在事实型单文档问题上可靠（single_hop Hit@5 高、top1 置信 0.85+），权限隔离严格。
2. 拒答阈值 0.3→0.7 标定后拒答准确率 0.938，剩余漏拒需生成层兜底。
3. 小语料下 dense 单路已很强；hybrid/rerank 的增益有限但架构保留（语料增长后的互补性与安全网价值）。
4. 延迟瓶颈明确：rerank top-50 CPU 推理，候选截断是第一优化（D26 已实施 50→20，零指标损失，延迟 -56%，见 §7.4）。
5. multi_doc 对比与阈值不可分的弱相关漏拒共同指向 Week 3 Agent 层的必要性。

### 7.2 评估驱动的三轮修复（0.857 → 0.952）

第一轮评估暴露 3 个 multi_doc 对比题全败 + 漏拒口径问题，逐层诊断并修复：

1. **对比题拆分检索**：router LLM 把完整对比问题原样发给 query_kb（词面偏向一侧）。先加 prompt 规则无效（LLM 仍重复同一 query），改为 **exec 层确定性正则兜底**：`'A和B的X有什么区别' → ['A的X', 'B的X']`，共享属性（'B的X'）自动补到左侧。不依赖 LLM 自觉。
2. **多 query_kb 结果合并**：原实现后一次调用整体覆盖前一次（last-write-wins）；改为按 chunk_id 去重合并（rerank 分高者胜），refused 语义改为「query_kb 全部拒绝才整体拒绝」（部分命中即视为有证据）。
3. **候选截断过紧**：qa-018 内部鉴权章节 RRF 排第 2，但 rerank 后掉到第 6（reranker 对「内部/公开」约束词区分不足），top_k=5 恰好截掉 → 生成层误判「文档章节缺失」。top_k 5→8 兜底（拒答阈值只依赖最高分，不受影响）。
4. **生成层对比规则**：答案「只罗列两侧要点、不做差异对照」稳定被判错（3/3）。GENERATE_SYSTEM 加规则：对比题必须逐点对照指出具体差异（「A 是 X，B 是 Y」）。
5. **漏拒口径**：qa-030 输出「未找到足够信息」但 refused 标志为 False。judge_leak 判「是否实质回答」：软拒答话术不算泄漏，只有实质回答（哪怕答非所问）才记 leak。

修复后 qa-018/019/021 全部转对；21 条应答仅剩 qa-016 判分波动（见 7.3）。

### 7.3 失败案例分析

- **qa-029「财务付款流程」（permission，唯一实质泄漏）**：fail-open 主题错位，非权限泄漏。admin 文档被角色过滤挡住（0 权限泄漏），但检索用 employee 可见的《差旅报销制度》《报销FAQ》答了「付款流程」（top1 0.881 高分弱相关，§3 已记录阈值不可分）。RAG 基线同样漏拒，Agent 层检索+生成两级都没拦住。后续方向：生成前主题一致性校验（问题主题 vs 候选主题）。
- **qa-016「第三方API限流规则」（judge 噪音）**：答案实质覆盖要点（限流维度/令牌桶/429/3000 次每分钟/沙箱 10%/提额 3 倍），但结尾多了一句「生产环境默认限额表格信息不足」的声明（生成层自相矛盾），引发 judge 分歧——独立重判 3 次 2 对 1 错。已把**多数表决**（判错时再判 2 次，≥2 错才定错）加入评估框架；本报告以单次判分为准，如实披露 0.952。
- **qa-030「内部订单API创建订单」**：软拒答口径问题。未泄漏受限内容，但 refused 标志语义不统一（话术拒绝 vs 标志拒绝），低优先级待办。

### 7.5 生成质量修复（D27，实测驱动）

用户实测「年假有几天」发现两个生成质量问题，修复后重跑完整评估验证：

1. **Markdown 表格缺分隔行**：GENERATE_SYSTEM 无表格格式约束，deepseek-chat 输出的表格没有 `|---|---|` 分隔行，前端渲染成一坨竖线文本。加规则 6：表格必须含分隔行，否则改用列表。
2. **制度冲突「甩锅」收尾**：检索到《考勤制度》《HR FAQ》与《年假与调休制度》年假标准不一致，旧输出以「请以人力资源部解释为准」收尾——问题没被解决，且与 qa-016 同类（结尾补充声明引发 judge 分歧）。加规则 7：指出冲突并给推荐结论（优先检索相关度更高的候选），不得以「请咨询XX」收尾。

修复后 qa-001 实测输出：表格格式正确；主动指出三份资料冲突并推荐「以《年假与调休制度》为准」+ 理由（专项制度、分档最细、检索相关度最高）。

### 7.6 结论

1. **Agent 层补上了基线做不到的三件事**：对比题多路检索聚合（3/3 修复）、带引用的生成（21/21）、L1 缓存（100% 命中，0.001s/条）。
2. **拒答准确率与基线持平（0.938），实质泄漏仅 1 条**，且为已知的 fail-open 主题错位而非权限越界——权限过滤在端到端链路中仍然 0 泄漏。
3. **评估框架本身被评估驱动改进**：judge_leak 口径、多数表决、拆分检索的确定性兜底，都是评估暴露问题后的产物。
4. 已知边界：主题错位（qa-029）需生成层主题校验；judge 对表格类/边界答案判分不稳定，多数表决是缓解不是根治。

## 8. 检索消融（D29）

5 组一键对比（`scripts/ablation_retrieval.py`，32 条 v1 集，报告 `data/reports/ablation_retrieval.json`）：

| 组 | Hit@5 | MRR | 拒答准确率 | 漏拒率 | 延迟/条 |
|---|---|---|---|---|---|
| dense（仅稠密） | **0.778** | **0.657** | 0.656 | 1.000 | 0.42s |
| sparse（仅自研稀疏） | 0.630 | 0.494 | 0.656 | 1.000 | 0.40s |
| hybrid_no_rerank（RRF 不重排） | 0.704 | 0.611 | 0.656 | 1.000 | 0.36s |
| hybrid（RRF + rerank，线上） | 0.741 | 0.560 | **0.938** | **0.182** | 8.90s |
| rank_bm25（库版对照，jieba 分词） | 0.667 | 0.481 | —（分数尺度不同，阈值不适用） | | |

结论（如实披露，与直觉不同的部分正是价值）：

1. **召回侧 dense 最强**：BGE-M3 稠密检索在 44 篇中文语料上 Hit@5/MRR 全面领先，RRF 融合稀疏路反而略降召回（0.778 → 0.741）。说明小语料 + 强 embedder 下，词法路对召回的边际贡献为负。
2. **rerank 的价值在拒答标定而非排序**：不加 rerank 的三组拒答准确率只有 0.656（漏拒率 1.000——所有应拒题都给了答案）。cross-encoder 分数的低置信阈值 0.7 是拒答防线的主体，Hit/MRR 的少量损失（-0.037）是这条防线的代价。
3. **自研稀疏路的独立质量低于库版 BM25**（0.630 vs 0.667）：自研 BM25 的价值在服务端集成（Qdrant 稀疏向量、无 Python 往返），单路质量不是它的卖点；RRF 下其贡献体现在长尾精确术语，本语料未显著受益。
4. **为什么保留 hybrid**：综合权衡——召回损失 3.7 个百分点，换拒答准确率 +28 个百分点（漏拒率 1.000→0.182，权限越界风险从"全漏"到"基本拦住"），对面向内部权限场景的产品是正确取舍。

## 9. 延迟拆解（D29）

计时埋点在 graph 节点层（`_lat` 读-改-写，避免 langgraph 浅合并覆盖），SSE 发 `latency` 事件 + 前端轨迹面板 + `/chat/metrics` 暴露 P50/P95。实测单条（未缓存，绩效考核问题）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| retrieval_rerank（20 候选交叉编码） | 10.7s | 50% |
| retrieval_embed（含 BGE-M3 首请求加载） | 5.0s | 23% |
| llm_generate（生成正文） | 2.1s | 10% |
| generate_ttft（首 token） | 1.4s | 7% |
| llm_router（flash 路由） | 1.0s | 5% |
| retrieval_bm25 / retrieval_qdrant / validate | <1s | ~1% |

结论与 D26 一致：延迟大头仍是 rerank（CPU 交叉编码），下一步是 GPU 推理或蒸馏小模型；embed 首请求含模型加载，稳态后占比下降。`/chat/metrics` 实测 P50/P95 = 19.84s（窗口含首请求冷启动）。

## 10. QA 集扩容与评估体系升级（D30）

- 32 → 120+ 条，6 场景（single_hop / cross_doc / comparison / out_of_corpus / permission / multi_turn）每类 jsonl 独立成文件（`data/qa_sets/v2/`）
- v2 字段：qa_id / question / role / gold_chunk_ids / answer_points（要点列表，judge 按点判分）/ expect_refusal / scenario_type / difficulty
- 新增：Wilson 置信区间（小样本比例估计）、失败归因（error_analysis.py：gold 未召回 / rerank 压下去 / chunk 切断 / 生成错误 / 误拒 / 漏拒 / 判分噪音）、judge_agreement.py（LLM-judge vs 人工 Cohen's kappa）、按场景分组指标
- 生成管线：LLM 批量造题 → 确定性 gold 解析（标题+章节关键词 → point id 快照）→ 角色可见性校验 → 去重

### 10.1 新集检索基线（2026-10-11，`eval_hybrid_20261011_205135.json`）

123 条 × hybrid 线上配置：

| 指标 | v1 32 条（§2） | v2 123 条 |
|---|---|---|
| Hit@5 | 0.741 | **0.794**（81/102 带 gold 条目） |
| MRR | 0.560 | **0.679** |
| 拒答准确率 | 0.938（漏拒 0.182） | **0.943**（应拒 34/40，漏拒 0.150；应答 82/83，误拒 1） |
| 延迟/条 | 8.90s | 7.09s（rerank 6.76s） |

按场景 Hit@5：single_hop 1.000（27/27）、multi_turn 1.000（17/17）、comparison 0.950（19/20）、cross_doc 0.947（18/19）、permission 0/19（**gold 从未出现在可见候选里 = 0 权限泄漏**，此处命中=0 正是设计目标）、out_of_corpus 无 gold 不适用。

**漏拒 6 条全部是 permission 场景的 fail-open 主题错位**（qa-029/030/169/170/174/178）：目标文档被权限过滤挡住（0 泄漏），但可见文档的高分弱相关（top1 0.73–0.91）越过阈值 0.7。与 §3「阈值救不了的 2 条」同一类问题，扩大样本后量化为 **6/19（32%）**——检索层对「问题主题 vs 文档主题」的错位没有区分能力；Agent 生成层的兜底效果因成本未在修复后重测，维持 §11.4 的已知边界。

**误拒 1 条 qa-127**（《服务条款》vs《隐私政策》对比，top1 0.302）：单次检索对跨文档对比题召回弱，Agent 层确定性拆分检索（§7.2-1）预期能救回，端到端验证。

### 10.2 评估集自检：检索反向校验抓出 3 条标签错误 + 4 条近重复

新集检索评估本身就是对 QA 集质量的一次交叉验证——3 条 out_of_corpus 题（qa-103 免费午餐/餐补、qa-157 补充医疗/体检、qa-164 外包人员节日礼品）被系统以 0.92/0.99/0.71 的高分答出，回溯语料确认 HR FAQ Q10/Q11、《外包人员管理规范》§1 确有明确答案，是**标签错误**而非系统故障。已改标 single_hop，gold 从 Qdrant payload 实测解析，重跑后 3 条全部命中、拒答准确率 0.913→0.937。

管线盲点（面试可讲）：gold 解析是确定性正向验证（LLM 声称的目标在索引中找得到才算数），但**验证不了负命题**——「问题在语料中真的没有答案」无法用同样的机制证明。教训：out_of_corpus 条目必须以系统本身做交叉验证（检索 top1 高分即告警），不能只信生成模型的「此题语料外」判断。

另外按「同 gold 集合 + 同场景」扫描抓出 4 条近重复（qa-150/138/151 与 qa-139/146/137 同义、qa-175 是 qa-170 的子集），已删除——生成管线的去重是精确归一化字符串匹配，抓不住单字插入的语义重复，最终集 123 条（multi_turn 17、permission 19，其余不变）。

## 11. Agent 端到端修复验证轮（D30 补记，2026-10-11）

### 11.1 L1 缓存污染事故（评估基础设施 bug）

123 条全量 agent 评估首跑得到 0.711，排查发现 36 条 cold 轮被历史评估的缓存答案直接命中（latency≈0.001s、retrieved 为空、旧答案按新 answer_points 判分），结果作废。根因：L1 缓存 key 只含 `kb_version`（跟语料走），**prompt/检索逻辑变更不推进版本**，改 prompt 后旧答案仍存活。

修复：`ExactCache.flush()` + `eval_agent.py` 冷轮前自动清空 `answer_cache:*`。教训（面试可讲）：缓存失效键要覆盖**所有**影响答案的输入，包括生成侧的逻辑版本，语料版本只是其中之一。

### 11.2 失败归因 → 5 处修复

对非污染条目的 17 条新鲜失败归因出 4 类模式，逐一修复：

| 模式 | 修复 |
|---|---|
| 生成自相矛盾（qa-147 引用规定却声称未找到） | 生成 prompt 规则 2 明令禁止，并补「缺失推断」：制度列明标准未提其他形式时按列明标准回答，不得以「未说明是否完整」拒答 |
| 对比题漏定位概括 | 规则 8：先各用一句话概括双方定位与侧重，再逐点对照 |
| 查询改写伤检索（qa-103 原题 top1=0.92 的 gold 被改写查询的相邻主题结果挤掉） | exec_tools 兜底：单个 query_kb 的 query 与原题不同且原题非对比句式时，原题也检索一遍，且**原题命中排在候选序列最前**（排序优先于改写查询的相邻结果） |
| 对比题拆分兜底失效 | `_split_compare_query` 两个 bug：v2 题统一带「？」使 `$` 锚点永不匹配；《》标题的「在X上/对X」共享属性句式不识别（只认「的X」）→ 去标点 + 《》边界取属性 |

### 11.3 针对性复测（32 条难点子集，`eval_agent_20261011_224241.json`）

考虑 API 成本未重跑全量，只跑改动影响面：comparison 全部 20 条 + 上轮 17 条失败项（并集 32 条）。修复前基线取上轮报告中**未被缓存污染的 24 条有效条目**（lat>1，其余 8 条 v1 迁移项是缓存命中，数字作废），同口径对比：

| 指标 | 修复前（24 条有效） | 修复后（同 24 条） |
|---|---|---|
| 正确率 | 7/24 = 0.29 | **13/24 = 0.54** |
| 其中 fresh v2 对比题 12 条 | 7/12 = 0.58 | **9/12 = 0.75**（qa-126/127 由拆分+排序修复直接救回） |
| Hit@5 | 23/24 | **24/24 = 1.00**（检索侧修复全部生效） |
| 漏拒 | — | **0**（拒答分支未受影响） |
| 保守拒答 qa-103 | 引用"餐补 30 元"仍称未找到 | 补规则 2 缺失推断后单独复测 **1/1** |

修复后 32 条全量快照：正确 17/32 = 0.53（该子集是失败项+全部对比题的难点集，不代表全量水平）。剩余失败 15 条归因：12 条**多 gold 覆盖不全**（每题 3-5 个 gold chunk，候选只命中其中 1-2 个；judge 要求的细节——HMAC 签名字段、EDR/7 天补丁、敏感区域等——在未召回的 chunk 里，生成无从答起，检索基线 Hit@5 0.794 已预示该上限）；3 条 judge 分歧票（qa-017/131/149，votes=2，边界噪音，多数表决按错计）。

### 11.4 结论与剩余边界

检索侧（拆分、兜底、排序）在难例子集上达到 Hit@5=1.00；生成侧对比题 0.65、无自相矛盾、无保守拒答。剩余主瓶颈是**检索深度**：多 gold 条目要求全 gold 进候选，方向是提高候选数/配额分配而非继续改 prompt。permission 场景 6 条 fail-open 主题错位（§10.1）在修复后的 agent 全链路重测因成本未做，维持「检索层无区分能力、需生成前主题一致性校验」的已知边界。
